19 · 分布式数据库与NoSQL

1一句话核心

分片分馆放数据，反规范化拿一致性换速度。

2先想后学：真实工程场景

🏗️ 场景商城大促：商品详情页 QPS 涨 40 倍，数据库 CPU 打满；架构会上抛出三个待决问题——① 热点数据放 Redis，用什么数据结构存排行榜和库存？② Redis 重启数据不能全丢，持久化选 RDB 还是 AOF？③ 单机 Redis 挂了怎么办？另外订单库要按用户分片拆到 8 台机器，应用层还要不要感知「数据在哪台机器」？
💡 点开看思路与答案

这三个问题就是案例题考了三次的 Redis 三件套：① 数据结构——排行榜用 ZSet（能按分数排序）、库存计数用 String、请求去重用 Set、消息队列用 List、对象用 Hash；② 持久化——RDB 是定期快照（恢复快、可能丢最近几分钟），AOF 是追加命令日志（丢得少、文件大恢复慢），生产常用两者混合；③ 高可用——主从复制（分馆抄本）、哨兵（自动故障转移）、Cluster（分片+高可用）。而「要不要感知在哪台机器」是透明性问题：中间件提供分片透明，应用就不用知道。缓存还要防三灾：穿透、击穿、雪崩。

3知识卡片

是什么

分布式数据库把逻辑上完整的数据物理上分散到多个节点：按行/列切开叫分片（水平分片=按行、垂直分片=按列、混合两者），每个分片可再复制多份。NoSQL（Not only SQL）是放弃部分关系数据库约束换取扩展性的非关系库家族，分四类：键值（Redis）、文档（MongoDB）、列族（HBase/Cassandra）、图（Neo4j）。

解决什么问题

单机有天花板：容量到顶、读写到顶、故障即全站瘫痪。分片解决容量与吞吐（各管一片），复制解决高可用与读扩展（分馆抄本），透明性解决「应用要不要操心这些」；NoSQL 则在关系模型太重（强 schema、强一致、多表连接）的场景下，用更简单的模型换海量吞吐。

核心机制一：透明性级别（考试爱排座次）

透明性（从高到低）应用无需知道什么类比
分片透明（最高）数据被切成了几片、按什么切只管向档案馆总台借「某档案」
位置透明该片存在哪个分馆知道档案名，不必知道在哪个馆
局部数据模型（映射）透明分馆内部用什么模型存知道在几号馆，不管馆内排架方式
复制透明（常并列叙述）数据复制了几份、同步到哪不知道也不必知道抄本有几份

跨节点的原子提交靠两阶段提交（2PC）：协调者先「预备」（各参与者表决能否提交），全票通过再「提交」，任一反对则全体回滚——它是 18 页事务原子性在分布式下的延伸。

核心机制二：CAP 与 BASE

CAP：一致性 C、可用性 A、分区容错 P 三者不可兼得；网络分区（P）在分布式环境下无法回避，实际是在 P 的前提下做 CP（保一致拒服务，如 ZooKeeper 类协调组件）或 AP（保可用容旧值，如多数 NoSQL）的取舍。BASE 是 AP 的工程化表述：基本可用、软状态、最终一致。

核心机制三：Redis 三件套（近 5 年案例考 3 次）

数据结构典型场景
String（字符串）缓存对象、计数器（库存、点赞数）、分布式锁
Hash（哈希）存对象的多字段（购物车：用户→商品→数量）
List（列表）消息队列、最新列表（时间线）
Set（集合）去重（抽奖去重）、共同好友（交集）
ZSet（有序集合）排行榜（按分数排序）、延迟队列
持久化机制优点缺点
RDB 快照定期把内存数据二进制落盘文件紧凑、恢复快两次快照之间的数据宕机即丢
AOF 日志追加每条写命令（可每秒刷盘）最多丢 1 秒数据文件大、恢复慢
混合持久化RDB 做底 + 增量 AOF恢复快且丢得少配置略复杂（生产常用）
模式机制定位
主从复制主写从读，主异步同步从（分馆抄本）读写分离 + 数据冗余；主挂需人工切换
哨兵 Sentinel监控主从，主挂自动投票提升从库为新主并通知客户端高可用（自动故障转移），不分片
Cluster 集群数据按 16384 个 slot 分片到多主，每主可带从分片 + 高可用一体，水平扩展

核心机制四：缓存三灾与对策

口诀：穿透库里无，击穿单个热，雪崩一大片。穿透=查根本不存在的数据，缓存永远不命中、请求全砸到库（对策：布隆过滤器快速拦截「肯定没有」、对空结果也缓存短时间）；击穿=某一个热点 key 恰好过期，瞬时洪峰全打在这个 key 上（对策：互斥锁只放一个请求回源重建、热点 key 逻辑过期不过期）；雪崩=大批 key 同时过期或缓存整体宕机，请求山崩式砸向数据库（对策：过期时间加随机打散、多级缓存、限流熔断降级）。

核心机制五：反规范化

规范化拆表换来「事实只存一处」，但查询要多表连接；分布式下跨节点连接更贵。于是有意冗余（如订单表冗余用户名）减少连接——这就是反规范化：拿一致性换速度的明码交易。交易条款要写清：冗余字段的同步更新策略（应用层双写、变更消息异步刷新、定时校对）与容忍的不一致窗口。

⚠️ 易错点① 透明性级别排序：分片透明最高、局部映射透明最低——「最高」问法常考。② CAP 不是「三选二」随便丢 P：P 必选，实际选 CP 或 AP。③ 主从复制是「异步抄本」，主挂瞬间最近的写可能没同步——损害的是持久性/一致性，不是可用性。④ 击穿与雪崩的区别在「一个热点」还是「一大片」，穿透在「库里根本无」。⑤ 反规范化不是「不设计」，是注明代价的设计，案例要写同步策略才给分。
🇬🇧 专业英语小贴士sharding / fragmentation（分片）、replica / replication（副本/复制）、NoSQL = Not only SQL，CAP = Consistency, Availability, Partition tolerance。

4生活类比与口诀

本页是 📚 中央档案馆的「开分馆」章节：一个馆装不下全城档案，就按区域分片开 8 个分馆（分片），每个分馆再抄一份副本藏于别处（主从复制=分馆抄本）；读者报档案名，总台自动路由到分馆（分片透明），连分馆烧了也能凭抄本接着服务（哨兵自动扶正）。缓存则是「总台旁的随手架」，随手架也有三灾，口诀专治。

类比项概念项成立/失效
按区域开分馆水平分片成立
分馆抄本异地存放主从复制 / 副本成立；抄是「异步」的，主馆刚记的账可能还没抄过去
总台统一受理，读者不问分馆分片/位置透明成立
随手架没货就先记「无货」小牌空值缓存 / 布隆过滤器成立；失效边界：随手架再快也变不出库里没有的数据——「穿透」的本质是数据缺失，不是缓存失职
为图省事在多个馆复抄同一份档案反规范化冗余成立；失效边界：现实抄本改一处漏一处没人管，数据库必须靠同步策略兜住一致性——「明码交易」的价签
分馆抄本主从备，哨兵盯梢自动替；
穿透库里无，击穿单个热，雪崩一大片；
布隆拦无、互斥护热、过期打散防连环；
反规范是笔交易，一致性换速度要写穿。

10小结

  • ① 分布式三板斧：分片扩容量、复制保可用、透明性让应用不操心（分片透明最高、局部映射透明最低）；跨节点原子性靠 2PC。
  • ② CAP 中 P 必选，实际选 CP（一致优先拒服务）或 AP（可用优先容旧值）；BASE=基本可用、软状态、最终一致。
  • ③ Redis 三件套（结构/持久化/主从哨兵集群）+ 缓存三灾口诀「穿透库里无，击穿单个热，雪崩一大片」；反规范化是拿一致性换速度的明码交易，必须写同步策略。
