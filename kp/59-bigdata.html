59 · 大数据架构

1一句话核心

Lambda 批流两条腿，Kappa 一条腿重放日志。

2先想后学：真实工程场景

🏗️ 场景某视频平台要建「播放日志分析平台」：每天新增 10TB 播放行为日志。运营要求大盘数据分钟级可见（热点内容晚半小时就没意义）；财务要求结算报表精确可审计，差一分钱都要查得清。方案 A：每晚跑一次全量批处理——财务满意，运营骂慢。方案 B：全部改成实时流式计算——运营满意，财务发现流式算出来的数偶尔对不平（乱序、迟到、重复），审计不敢签字。问题：架构上有没有办法让两条需求同时满足？代价是什么？能不能只用一套代码？
💡 点开看思路与答案

有，这就是 Lambda 架构：同一份数据走两条腿——批处理层每天对全量数据算出精确视图（喂饱财务），加速层对增量数据流实时算出近似视图（喂饱运营），服务层把两个视图合并后统一对外查询。代价：同一业务逻辑要写批、流两遍，改一个口径要改两处代码，维护成本翻倍。如果团队小、想只留一条腿，就是 Kappa 架构：一切皆流，用 Kafka 把全量日志存住，需要精确重算时重放日志从头再算——省掉两套代码，但重放要吃大量算力，且复杂批逻辑在流引擎上不好写。

3知识卡片

是什么：大数据的 5V 特征

大数据不是「数据多」，而是「多到传统单机数据库在成本与技术上都玩不转」。特征用 5V 概括（不同教材口径略有差异，考试建议把两种口径都点到）：

V含义一句话理解
Volume 大量规模从 TB 到 PB 级多到一台机器装不下、算不完
Variety 多样结构化/半结构化/非结构化表格、日志、图片、视频什么都有
Velocity 高速产生与处理速度快数据像洪水一样涌来，边到边算
Value 价值密度低整体价值大但稀释一小时监控里只有几秒有用
Veracity 真实性质量参差、噪声多第 5V 的常见口径；另有口径把 Value 换成 Veracity，答题时注明即可

Hadoop 生态：三驾马车

HDFS（分布式文件系统）：把大文件切块分散存在一堆便宜的商用机上，每块默认存 3 个副本容错；设计假设是「一次写入、多次读取」的大文件顺序读，主从结构（NameNode 管目录元数据，DataNode 存数据块）。MapReduce：计算模型，把任务拆成 Map（每台机器各自算自己那块数据——「移动计算不移动数据」）和 Reduce（汇总结果），中间结果写磁盘。YARN：资源调度器，管整个集群的 CPU/内存，谁想跑计算先找它申请资源。三者关系：HDFS 管存、YARN 管资源、MapReduce/Spark 管算。

维度MapReduceSpark
中间结果每步落盘，读写磁盘频繁基于内存（RDD 弹性分布式数据集），迭代时不用反复读写磁盘
速度慢，适合超大规模离线作业内存计算，迭代与交互式场景快一个量级（一般认为，视任务而定）
代价稳、省内存吃内存，内存不足会退化甚至失败

周边常客：Hive 用 SQL 语法查 HDFS 上的数据（数据仓库工具）、Kafka 分布式消息队列（40 页的「快递中转站」，流式管道的入口与日志底座）。

Lambda 架构：批流两条腿

三层职责必须记牢：批处理层（Batch Layer）持有全量数据集，周期性重算出「准而慢」的批视图；加速层（Speed Layer）只处理最新增量数据，算出「快而不完全准」的实时视图；服务层（Serving Layer）把两路视图合并后统一响应查询。优点：准确性与实时性兼得；缺点：同一逻辑批流各写一遍，口径一改要改两处，测试维护成本翻倍。

Kappa 架构：只留流式一条腿

核心主张：既然流式迟早能算一切，那就只保留流处理。用 Kafka 这类日志系统持久保存全量数据（按主题分区、保留足够长的时间），所有计算都是流式作业；当逻辑变更或历史算错时，启动新版本作业从日志重放（replay）重新计算，算完切换结果。优点：一套代码、一套引擎；缺点：重放历史要吃大量算力与时间，复杂批处理逻辑（如全量机器学习训练、超大规模连接）在流引擎上表达困难，且依赖日志系统能存得下、存得住。

数据湖 vs 数据仓库 vs 湖仓一体

维度数据仓库数据湖湖仓一体（Lakehouse）
建模时机先建模后写入（schema-on-write）先存原始后定义（schema-on-read）湖的存储 + 仓的治理
数据类型结构化为主任意格式原始数据一份原始存储，多种访问
优势质量高、口径统一、BI 快便宜、灵活、万物可存同时支撑 BI 报表与 AI 训练，避免两套存储互拷
短板建模周期长、存不了非结构化无事务无治理，容易变「数据沼泽」需要新的表格式与元数据管理（如支持 ACID 的开放表格式）

CAP 在分布式存储的取舍（呼应 19 页）

数据一旦分散到多台机器，CAP 就躲不开：CAP 即一致性（C）、可用性（A）与分区容忍（P）三者的取舍，网络分区（P）必选，实际是在 CP 与 AP 之间取舍。经验口径：面向日志查询、大盘看板的存储多取 AP + 最终一致（宁可几秒旧值，不能查不动，对应 BASE）；面向结算、审计的链路取 CP（宁可慢、不可错）。Lambda 的「批视图为准」本质上也是拿时间换一致性——批层结果就是最终一致的「正确答案」。

🔤 专业英语Lambda Architecture（兰姆达架构，批流混合架构）· Stream Processing（流式计算）· Data Lakehouse（湖仓一体）
⚠️ 易错点① Kappa 不是「Lambda 删掉批层」这么简单：它成立的前提是日志系统能持久保存全量数据并支持重放；② 重放≠免费：把「重新过滤一遍水」当成零成本是典型错误，重放要重吃一遍算力；③ 加速层的数据「快而不完全准」——乱序、迟到、重复要靠批层修正，别把它吹成精确计算；④ HDFS 面向「一次写入多次读取」，拿它频繁随机改小文件是用错了场景（随机更新找 HBase 类系统）；⑤ 5V 的第五个 V 存在口径分歧（Value 或 Veracity），答题写全并注明口径；⑥ 数据湖不等于没治理，「先存了再说」存出来的常是数据沼泽。

4生活类比与口诀

未来新城里，大数据=全城摄像头与水厂：几十万个摄像头日夜产生海量录像（5V 的数据源），这些水最终要供到全城。城市供水系统正好对应数据架构：数据湖=水库——什么水都先蓄起来，生水、雨水、浑水来者不拒（schema-on-read）；数据仓库=自来水厂——按标准工艺过滤消毒，出水干净但建厂慢、只认规定的进水（schema-on-write）；湖仓一体=水库水厂一体化管理——同一池水，既能直接给农田灌溉（AI 训练吃原始数据），又能净化后进管网饮用（BI 报表）。Lambda=双管供水：老管道每天凌晨集中沉淀过滤（批处理层，水最干净但隔天到），快速管道简单过滤直接送（加速层，立刻到但偶尔夹泥沙），两股水在你家水龙头汇合（服务层）。Kappa=只留快速管道，但管道口装了个「可回放的总阀门」——哪段水不干净，把那段重新过滤一遍（重放日志）。

类比项概念项成立/失效
水库什么水都蓄数据湖 schema-on-read成立
水厂按标准工艺出水数据仓库 schema-on-write成立
快速管道+沉淀管道双管供水Lambda 批流两路+服务层合并成立
回放阀门重新过滤零成本Kappa 重放日志失效：重放要重新消耗一遍算力与时间，数据量越大越贵；且复杂批逻辑在流引擎上未必写得出来
摄像头日夜忙，五V数据进库房；
湖是水库仓是厂，湖仓一体不分家；
Lambda 两条腿，批准流快最后汇；
Kappa 一条腿，重放日志把账追；
HDFS 存大块，YARN 调度算得快。

✍️ 论文写作素材，需结合自身项目改写
  • 论点句式：「针对『实时看板分钟级 + 结算报表精确可审计』的双重需求，我采用 Lambda 架构：批处理层基于全量数据生成精确视图，保证结算口径一致、可审计；加速层对增量数据流实时计算，保障看板秒级时效；服务层合并双视图统一响应，对用户屏蔽批流差异。」
  • 论点句式：「考虑到团队规模有限、希望只维护一套计算逻辑，我们选择 Kappa 架构：以 Kafka 持久保存全量日志作为唯一事实来源，所有计算统一为流式作业；需修正历史指标时重放指定时间段的日志重算并覆盖结果。」
  • 项目情景模板：日志分析平台 / 用户行为埋点分析 / 实时风控特征 + T+1 财务对账。论证主线：背景 → 双时效需求矛盾 → 选型论证（逐条映射需求）→ 分层设计 → 量化收益（时延从 T+1（隔天出数）到秒级、对账差错率下降）→ 遗留问题（两套逻辑维护成本 / 重放算力开销）。
  • 论点句式：「原始多源异构数据先统一入湖，保证接入灵活；随后出现找数难、口径乱的问题，我们引入统一元数据中心与支持 ACID 的湖仓表格式，使同一份存储同时支撑 BI 报表与模型训练。」
  • 备考提示：Lambda 与湖仓一体均为近年论文考过的方向（据公开考情梳理）。写技术论文务必落到「为什么选它、代价是什么、效果如何验证」，避免堆砌产品名词。

易混概念对比

Lambda 架构Kappa 架构
计算腿批处理层 + 加速层两条腿，服务层合并只留流式一条腿
历史重算批层天然重算全量重放 Kafka 日志重新消费
易错点以为两套代码是优点（实为最大维护负担）以为「删掉批层就省事」——重放算力开销与复杂批逻辑受限是它的隐形成本
一句话区分Lambda 花两套代码买「准与快兼得」，Kappa 花重放算力买「一套代码走天下」。

10小结

  • ① 大数据 5V（大量/多样/高速/价值密度低/真实性，第五V注意口径）；Hadoop 三驾马车：HDFS 管存、YARN 管资源、MapReduce/Spark 管算，Spark 靠内存计算在迭代场景快。
  • ② Lambda=批处理层（准而慢）+加速层（快而不完全准）+服务层（合并双视图）；Kappa 只留流式一条腿，靠重放日志重算历史——一套代码换重放算力。
  • ③ 数据湖存生水（schema-on-read）、数据仓库出净水（schema-on-write）、湖仓一体一份存储同时养 BI 与 AI；分布式存储的取舍仍逃不出 19 页的 CAP。
