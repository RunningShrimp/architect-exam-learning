36 · 架构风格：MVC、微内核与SOA

1一句话核心

MVC 分工界面数据控制，微内核最小核心装插件，按场景选风格。

2先想后学：真实工程场景

🏗️ 场景某团队做运营后台：同一份商品数据要有「表格视图」「卡片视图」「大屏视图」三种展示，还要出手机版。最初代码把查询数据库、计算折扣、渲染 HTML 写在同一个 JSP 文件里。结果是：改一个折扣规则要改三个页面；美工改样式经常弄坏业务逻辑。应该怎么拆？拆完之后，用户的一次点击在这几块之间是怎么传递的？
💡 点开看思路与答案

典型的「界面与数据纠缠」。用 MVC 拆开：Model 管商品数据与折扣规则（厨师做菜）、View 管三种展示（菜单摆盘）、Controller 接收请求并调度（服务员接单）。一个 Model 配多个 View，改规则只动 Model，改样式只动 View。用户点击的流向：Controller 接收→调 Model 更新→View 观察 Model 变化刷新（观察机制，正是 35 页隐式调用的应用）。

3知识卡片

是什么：MVC 与它的两次进化

MVC（Model-View-Controller）是交互式应用最常用的特定领域风格。餐厅比喻：Model=厨师（管数据与业务规则，不理谁在吃）、View=菜单摆盘（管展示，可多套摆法对应同一锅菜）、Controller=服务员（接单、协调厨房与餐台）。交互主线：用户→Controller→Model→（Model 状态变化）→View 观察刷新→用户看到。一个 Model 可对应多个 View，界面与逻辑互不拖累。

变体关键变化代价/收益
MVPView 完全被动，Presenter 居中全权中介，View 与 Model 不再直接往来交互逻辑集中、View 好做单元测试；代价是 Presenter 变「胖」
MVVMViewModel + 数据绑定：View 与 ViewModel 状态自动双向同步前端框架主流（界面自动跟数据走，手写同步代码消失）；代价：绑定调试不直观、大项目绑定关系复杂

微内核（Microkernel）：最小核心 + 插件

微内核只把最核心、最稳定的功能放进内核（如操作系统的进程调度、内存管理、进程间通信），其余功能做成插件（plug-in），通过内核提供的扩展点注册接入、经内核消息通信。典型：微内核操作系统、浏览器插件、IDE（Eclipse 式插件体系）、规则引擎容器。

  • 优点：核心小而稳定；扩展灵活（加功能=加插件）；插件故障可被隔离，不至于拖垮核心；便于第三方开发扩展。
  • 缺点：插件间/插件与核心的通信都要经核心转发，性能有开销；「什么放核心」的边界设计最难。

DSSA：垂直域 vs 水平域

DSSA（特定领域软件体系结构）：在一 个特定应用领域内，以「领域分析→领域设计→领域实现」为基本活动，产出一套可复用的参考架构。垂直域=同一行业的端到端完整应用域（如电信 BOSS、银行核心系统）；水平域=跨行业通用的功能域（如工作流引擎、报表、消息中间件）。考试给一段「行业专用平台」选垂直域、给「通用组件平台」选水平域。

⚠️ 易错点① MVC 里 View 不是自己拉数据刷新，而是观察 Model 的变化（通知机制）；② MVP 与 MVC 的分界：View 与 Model 是否还有直接联系——MVP 彻底断开；③ MVVM 的「VM」是 ViewModel 不是 View-Model 混写；④ 微内核的插件不能互相直接调用，通信经核心转发（性能缺点来源）；⑤ DSSA 垂直域≠大系统、水平域≠小系统——区别在「单一行业纵深」还是「跨行业通用」。

4生活类比与口诀

MVC=一家餐厅：你（用户）点菜从来不进厨房，服务员（Controller）把单子递给后厨，厨师（Model）做好菜不亲自端，摆盘上桌（View）你才看见；菜单换了样式不影响菜谱，菜谱改了口味不用重印菜单。微内核=精简市政厅+专业外包：市政厅只保留户口、审批两件核心事，绿化、停车、垃圾清运全外包给专业公司（插件），哪家外包倒闭了市政厅照常运转，换一家重新签（插件热插拔）。

类比项概念项成立/失效
服务员接单传菜Controller 接收请求并调度成立
厨师不管谁来吃Model 不依赖具体视图成立
一桌菜多种摆盘一个 Model 多个 View成立
服务员知道菜的具体做法Controller 掌握业务规则失效：业务规则归 Model，Controller 只做接收与调度，混了职责就成「胖控制器」反模式
市政厅只留核心、其余外包微内核：最小核心+插件成立
MVC 餐厅三分手：厨师模型菜是数据；
服务员接单控制器，摆盘视图给客看；
MVP 断开模与视，MVVM 绑定自动换；
微内核里留核心，插件来了随便换；
垂直域里一条龙，水平域里通用件。

易混概念对比

MVC多层架构（三层）
关注什么一个应用内部的职责分工：界面/数据/控制部署拓扑上的分层：表现层/业务层/数据层（37 页）
解决的问题界面多变、数据复用、交互解耦客户端与服务器职责划分、集中管理业务
易错点以为 MVC=三层——MVC 三件可以全跑在同一台服务器上以为分了层就等于用了 MVC——两套坐标不同，可独立也可组合
一句话区分MVC 是厨房里的分工（谁做菜谁摆盘），三层是楼里的分工（几楼点菜几楼炒菜）。

10小结

  • ① MVC：Model 管数据规则、View 管展示（观察刷新）、Controller 管接收调度；MVP 断开 View-Model，MVVM 用数据绑定自动同步。
  • ② 微内核=最小核心+插件：核心稳定、扩展灵活、故障可隔离，代价是通信经核心转发的性能开销。
  • ③ DSSA 垂直域是行业纵深、水平域是跨行业通用；「给场景选风格」背熟本页信号词表。
